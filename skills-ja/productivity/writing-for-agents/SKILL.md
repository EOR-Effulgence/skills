agent が読むあらゆる文書 — skill、`AGENTS.md` / `CLAUDE.md`、ポインタ経由で到達されるドキュメント — を書くためのリファレンス。包装は違っても、書き方は違わない: 同じレバーがどれをも予測可能にする — agent が毎回同じ _process_ を取ること、同じ出力を生むことではない。

書いている文書が skill なら、frontmatter・invocation の選択・router skill については [`SKILL-MECHANICS.md`](SKILL-MECHANICS.md) を読め。

## Context pointers

**context pointer** とは、agent の context に保持され、context の外にある素材を名指しし、そこへ到達する条件を符号化した参照だ。skill の description はその一つであり、`AGENTS.md` でドキュメントを名指しする 1 行も同じものだ。agent がその素材へいつ到達するか — そしてどれだけ確実に到達するか — を決めるのは、ポインタの指す先ではなく、その _言い回し_ の方だ。必ず読ませたい対象が弱い言い回しのポインタの背後にあるなら、それは variance のバグだ: まず言い回しを研ぎ澄ませ。素材をインライン化するのは、研いでも駄目だったときだけにしろ。

ポインタは 2 つの仕事をする — 素材が何であるかを述べること、そして到達を発火させるべき **branches** を列挙すること（branch とは、その文書が扱う別個のケースであり、実行ごとに文書内の異なる経路を通らせるものだ）。常時ロードされるポインタは 1 語ごとに毎ターンのコストを払うので、本文よりさらに厳しい pruning に値する:

- **leading word を前に置く** — ポインタこそが、その語が発火の仕事をする場所だ。
- **1 branch につき 1 トリガー。** 単一の branch を言い換えただけの同義語は、1 つの branch を二度書いているにすぎない。collapse させ、本当に別個の branch だけを残せ。
- **本文に既にある素性は削れ。**

## 2 つの load

追加するあらゆる文書とポインタは、2 つの予算のどちらかを費やす:

- **Context load** — 常時ロードされる素材が agent の window に課すコスト: `AGENTS.md` の 1 行、skill の description、毎ターン context に居座り、発火するしないに関わらずトークンと注意を費やすもの全般。
- **Cognitive load** — 人間に課すコスト: どの文書が存在し、いつどれに手を伸ばすか。索引は人間自身だ。最小化すべきコストではない — 人間の主体性の対価であり、人間の判断が効く場所では費やし、効かない場所では取り除け。

ポインタ経由でのみ到達される素材は、ポインタ自身の 1 行と引き換えに context load を免れる。ポインタすら持たない素材は、まるごと cognitive load に乗る。

## Information hierarchy

文書は 2 つのコンテンツ型 — **steps**（agent が順に実行するアクション）と **reference**（必要に応じて参照される定義・ルール・事実）— から作られ、それらは自由に混ざる: 全部 steps（レシピ）、全部 reference（レビューのルール群、この skill）、あるいは両方。核心となる判断は、各要素が **information hierarchy** のどこに位置するかだ。これは agent がその素材をどれだけ即座に必要とするかで順位づけした梯子である:

1. **In-file step** — 最上位の階層: agent が何を、どの順で行うか。
2. **In-file reference** — 必要に応じて参照される。しばしば正当にフラットな peer-set（レビューの全ルールが同一段に並ぶ）になる — これは良い配置であって、smell ではない。
3. **Disclosed reference** — 別ファイルへ押し出され、context pointer から到達され、ポインタが発火したときにのみロードされる reference。同じフォルダの兄弟ファイルから、どこにでも存在しどの文書からでも指し示せる完全な external reference までの幅を持つ。

下へ押し込む量が少なすぎれば頂点が膨れ、多すぎれば agent が実際に必要とする素材を隠してしまう。この緊張こそが判断のすべてだ。

**Progressive disclosure** とは、この梯子を下る動き — 本体ファイルから出し、ポインタの背後へ置くこと — であり、頂点を読めるまま保つためのものだ。主目的はトークン最適化ではない: 階層を守る手段だ。branch は最もきれいな disclosure の判定基準になる: すべての branch が必要とするものはインラインに、一部の branch しか到達しないものはポインタの背後へ。文書が steps を持つとき、disclose すべき in-file reference は steps を埋もれさせ、それらに注意を向けるかどうかをコイン投げに変える — これは可読性だけでなく variance のレバーだ。

**Co-location** はファイル内側の相棒だ: 梯子が _どこまで下へ_ 置くかを決めるのに対し、co-location はそこに置いたとき _何が隣に並ぶか_ を決める。ある概念の定義・ルール・注意点を散らさず 1 つの見出しの下にまとめ、一部を読めば隣接部分も一緒に付いてくるようにしろ。判定基準: その文書は agent 向けに書かれたドキュメントとして読めるべきだ — まとまった素材はそう読め、散らばった素材はそう読めない。（duplication とは別物だ: あちらは 1 つの意味を 2 か所で繰り返す。散乱は 1 つの意味を多数へ断片化する。）

**Sprawl** がここでの failure mode だ: すべての行が生きていて重複が無くても、単に長すぎる文書。注意は余分に薄く広がり、余計な 1 行は関連性を保ち続けるべき対象を 1 つ増やす。治療は梯子だ: reference をポインタの背後へ disclose し、branch か sequence で分割して各経路が必要なものだけを運ぶようにしろ。

## Steps と completion criteria

あらゆる step は **completion criterion** — 作業が完了したことを agent に告げる条件 — で終わる。これをレバーたらしめる性質が 2 つある:

- **Clarity** — agent は完了と未完了を見分けられるか? 曖昧な境界（「共通理解に達した」）は **premature completion** を招く: 本当は終わっていないのに step を切り上げ、注意が _終わったこと_ の方へ滑る。まだ見えている後続の step — **post-completion steps** — が引力を生み、criterion の明快さが抵抗になる。防御は順番どおりに: **まず境界を研げ**（局所的で安い）。境界が本質的に曖昧で _かつ_ 実際に急ぎが観測されたときにだけ、sequence を分割して後続の step を隠せ — そして隠すことが効くのは本物の context 境界を跨ぐときだけだ（hand-off か subagent への dispatch。インラインの呼び出しは後続の step を context に残したままで、何もクリアしない）。
- **Demand** — どれだけを要求するか。「変更されたすべての model を漏れなく扱う」は徹底した作業を強いるが、「change list を作れ」は強いない。demand は **legwork** — agent が作業の内側で行う掘り下げで、独立した step としてではなく言い回しの中に潜んでいるもの — を駆動する。しかもこれは step に縛られない: 「every step done」が一連の並びを縛るのと同じように「every rule applied」はフラットな reference を縛る。全部が reference の文書でも網羅性の水準を運べるのはそのためだ。

最も強い criterion は、checkable であり、かつ exhaustive でもある。

## いつ分割するか

1 つの文書を 2 つに分けることは 2 つの load のどちらかを費やす。だから分割は、その切り分けが元を取るときだけにしろ:

- **sequence で分ける** — 後続の step が目の前の step を急がせる誘惑になっている一連の並びを切る。それらを視界の外に置くことが、現在のタスクへのより深い legwork を駆動する。逆方向にも注意しろ: sequence を統合すると、各 step の後続が次に来るものへ露出し、premature completion を招く。
- **invocation で分ける** — skill 固有: [`SKILL-MECHANICS.md`](SKILL-MECHANICS.md) を参照。

## Leading words

**leading word** とは、モデルの pretraining にすでに存在し、文書を実行しているあいだ agent がそれで思考する、圧縮された概念だ（_lesson_、_fog of war_、_tracer bullets_）。文としてではなくトークンとして繰り返されることで、分散した定義が積み上がり、最少のトークンで振る舞いの一領域を丸ごと固定する。モデルがすでに持つ prior を呼び出すからだ。自分で造語しても、明快に定義すれば機能する。ただし作り物の語は何の prior も呼び出さない — pretraining 済みの語なら無料で得られるものを、定義のトークンで払うことになる。まず既存の語に手を伸ばせ。

leading word は 2 度固定する。本文では _execution_ を: その語が現れるたび、agent は毎回同じ振る舞いへ手を伸ばし、フラットな reference の内側では、探すべき対象のクラスへ注意を絞る。ポインタでは _invocation_ を: 同じ語があなたのプロンプト、ドキュメント、コードベースに共通して住んでいると、agent はその共通言語を素材に結び付け、より確実に到達する。

leading word で refactor できる機会を狩れ。3 か所で綴られた三つ組、1 つのアイデアを指すのに 1 文を費やしているポインタ — どれも単一のトークンへ畳み込まれたがっている一節だ:

- "fast, deterministic, low-overhead" → _tight_（_tight_ な loop）。
- "a loop you believe in" → _red_ — 曖昧なゲートが、二値の観測可能な状態になる（loop はそのバグで _red_ になるか、ならないか）。

二重に勝てる: トークンが減り、agent が思考を掛けるフックが鋭くなる。あらゆる文書は leading word が引退させられる言い換えを抱えていると想定しろ — 探しに行け。

このレバーの隣にある failure mode が **negation** だ: 禁止による誘導は、禁じた振る舞いを context へ引きずり込み、かえって _利用しやすく_ する。_象のことを考えるな_ と言えば象しか残らない。否定は弱い修飾でしかなく、強く活性化した概念に押し切られるため、禁止は半分「それをやれ」という指示として読まれる。**肯定** で促せ — 目標の振る舞いを述べ（「1 行のコメントを書け」）、禁じた方は口にすらするな。禁止が居場所を得るのは、肯定形で言い表せない硬いガードレールとしてだけであり、その場合でも肯定的な目標と組にして、注意が「何をするか」に着地するようにしろ。

## Pruning

- 各々の意味は **single source of truth** に保て: 権威ある場所は 1 つだけにし、振る舞いの変更が 1 か所の編集で済むようにする。**Duplication** — 同じ意味が 2 か所以上にあること — は保守とトークンのコストを払わせ、さらにその意味の梯子上の際立ちを実際の順位より上へ水増しする。（leading word のうっかりした裏返しだ。あちらは意図してトークンを繰り返すのであって、意味を繰り返すのでは決してない。）
- **environment** もまた source of truth だ — `package.json` の scripts、config ファイル、ディレクトリ構成、`--help` の出力 — そしてそれを言い直す文書は **cache** だ: 参照結果のコピーであり、その参照が高コストなときにだけ load に見合う。agent が見に行っても分からないものを cache しろ: 明文化されていない慣習、選択の背後にある理由、どの config も白状しない罠。1 ファイル・1 コマンドで済む参照は environment に任せろ。そこなら陳腐化しようがない。
- すべての行を **relevance** で点検しろ: それはまだ文書のすることに関わっているか? 行が relevance を失うのは、そもそもタスクに関わっていない（単なる説明、あるいは disclose すべき branch）か、記述している振る舞いや世界が変わって陳腐化したときだ。短い文書ほど relevance を保ちやすい。pruning の規律が無いときの既定の末路が **sediment** だ: 足すのは安全に見え、消すのは危険に見えるがゆえに堆積した古い層で、まだ生きているものを見つけるにはそれをボーリングして掘り抜くはめになる。
- **no-op** を 1 文ずつ狩れ: モデルがデフォルトで既に従っている指示は、何も言わないために load を払っている。判定基準 — それはデフォルトと比べて振る舞いを変えるか? — は読者相対ではなくモデル相対だ: 2 人が no-op について意見を違えるとき、違えているのはデフォルトについてであり、決着は議論ではなく文書を走らせることでつける。文が落第したら、語を削るのではなく文ごと消せ。この判定基準は leading word も採点する: デフォルトを上回れないほど弱い語（agent が既にそこそこ徹底的なのに _be thorough_）は no-op であり、直し方はより強い語（_relentless_）であって、別の技法ではない。
