# Logic Prototype

自己完結した単一の HTML ファイル — **共有可能なデモ** — で、誰でもボタンをクリックして状態モデルを駆動できるもの。問いが **business logic、状態遷移、データ形状** に関するもの — 紙上では妥当に見えるが、実ケースを通してみて初めて違和感が出るもの — に対して使う。

インストールするものが何も無い 1 ファイルなので、非開発者 — デザイナー、PM、domain の専門家 — にそのまま手渡し、モデルを自分の手で感じてもらえる。だからこのデモはコードの言葉ではなく、彼らの言葉で話す。

## これが正しい形になるとき

- 「この state machine が X のあと Y が来る edge case を処理できるか自信がない」
- 「このデータモデルで … のケースを本当に表現できるのか」
- 「書く前に API がどうあるべきか触って感じたい」
- 誰かが **ボタンを押して状態の変化を見たい** もの全般。

問いが「これはどう見えるべきか」なら分岐違い。[UI.md](UI.md) を使う。

## プロセス

### 1. 問いを明文化する

コードを書く前に、どの状態モデルの、どの問いをプロトタイプしているかを書き留める。1 段落でいい。デモの先頭に置く（コメントではなく、見える形のイントロとして）。間違った問いに答える logic プロトタイプは純粋な無駄だ — 後で確認できるよう問いを明示しておく。ユーザーが今見ていようと、AFK で後から戻ってこようと変わらない。

### 2. ロジックを移植可能な module に隔離する

実ロジック — 問いに答えている部分 — を単一の `<script>` ブロックに置き、小さく純粋な module として書く。後で本物のコードベースに持ち上げてそのまま落とし込めるようにする。周りのページは使い捨て。この module はそうではない。

正しい形は問いによって変わる:

- **純粋な reducer** — `(state, action) => state`。アクションが離散的なイベントで、状態が単一の値のときに良い。
- **state machine** — 明示的な状態と遷移。「今この瞬間そもそもどのアクションが合法か」が問いの一部のときに良い。
- **平らなデータ型に対する純粋関数の小さなセット**。暗黙の現在状態がなく、ただの変換だけのときに良い。
- **明確なメソッド面を持つクラスや module**。ロジックが本当に継続的な内部状態を所有するとき。

問われている問いに最も合う形を選ぶこと。ページに繋ぐのが最も楽な形*ではない*。純粋に保て: DOM なし、`document` なし、内部に手を伸ばすボタンハンドラなし。ページがそれを呼び込む。逆方向には何も流れない。これがプロトタイプを自身の寿命を超えて有用にする鍵だ: 問いに答え終わったとき、検証済みの reducer / machine / 関数群は、単体で本物の module へ持ち上がる。

### 3. 共有可能な HTML ファイルを作る

1 ファイル、素の HTML/CSS/JS — フレームワークなし、bundler なし、サーバーなし。すべてインラインにして、ダブルクリックで開き、メールで回されても壊れないようにする。誰でもファイルを開くだけで動かせるべきだ。

非開発者に向けて書け。ラベルはすべて **domain の言葉** で書き、コードの言葉では書かない — ボタンも状態も、reducer ではなくビジネスとして読める。何が起きているかを平易な言葉で説明する。

上から下へ、きれいな階層でレイアウトする:

1. **タイトルと 1 行の説明** — このデモで何を探索できるのか（step 1 の問い）。
2. **現在の状態** — 関連する状態の全体を、読めるパネルとして描画する（生の JSON ダンプではなく、ラベル付きのフィールド）。クリックのたびに再描画し、変化が見えるようにする。非開発者が追いやすくなるなら、いま何が変わったかを明示する。
3. **自由に押せるボタン** — アクションごとに 1 つ、常に押せる状態で置き、誰でも好きな順にモデルをつつけるようにする。クリックのたびにそのアクションを dispatch し、状態を再描画する。
4. **ガイド付きウォークスルー** — **シナリオ** 群をタブ 1 つにつき 1 本ずつ置く。各タブには、そのシナリオの平易な短い説明 — どんな状況を作り、何に注目すべきか — と、その下にシナリオ用の **押すべきボタン** を順番に並べる。各ステップは本物のボタンだ: クリックするとそのアクションが実行され、次のステップへ進む。ウォークスルーを開始すると既知の初期状態にリセットされ、シナリオは毎回同じように走る。

シナリオは、扱いにくいケースを見せるものを選べ — happy path、厄介な edge case、本来なら不正であるべき操作の試み — 紙上では推論しづらいものを。

美しく、しかし抑制的に保て: きれいなタイポグラフィ、ゆったりした余白、アクセントカラーは 1 色。アニメーションなし、ギミックなし — 状態とボタンと張り合うものは置かない。

### 4. 引き渡す

ファイルを送るか、代わりに開いてやる。相手は自分のタイミングでウォークスルーをクリックし、自由に触る。面白い瞬間は「待って、これは起こりえないはずだ」「あれ、X はこうじゃないと思ってた」と言うときだ — それが _アイデア_ そのもののバグであり、それこそが全ての要点だ。新しいアクションや新しいシナリオを足したいと言われたら足す。プロトタイプは進化する。

### 5. 答えとプロトタイプを捕捉する

プロトタイプが問いに答え終わったら、まず答えを捕捉し、次に [SKILL](SKILL.md) が述べるやり方でプロトタイプを捕捉する。logic 固有の対応付けはこうだ: 検証済みの reducer / machine / 関数群は本物の module へ持ち上がる（判断が吸収される）。HTML シェルは、プロトタイプを一次情報 (primary source) として保つ使い捨てブランチへ一緒に乗っていく — 自己完結した 1 ファイルなので、そこでも自明に再実行できるままだ。

## アンチパターン

- **テストを足すな。** テストを必要とするプロトタイプはもうプロトタイプではない。
- **本物の database に繋ぐな。** 問いが明示的に永続化についてでない限り、インメモリの状態を使う。
- **一般化するな。** 「あとで X をサポートしたくなったら」は無し。プロトタイプは 1 つの問いに答える。
- **ロジックとページを混ぜてぼかすな。** 純粋な module が DOM、`document`、ボタンハンドラを参照していたら、もう持ち上げられない。ページは純粋な module の上の薄いシェルに留めろ。
- **フレームワーク・bundler・サーバーに手を伸ばすな。** 受け取った人がダブルクリックする 1 ファイルだ。React アプリや dev server は「共有可能」を台無しにする。
- **HTML シェルを production に出荷するな。** ページは手でクリックされることに最適化されている。残す価値があるのは、その背後にあるロジック module の方だ。
