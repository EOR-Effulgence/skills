# Phase boundaries

**phase** とはセッション内の作業のかたまりだ: grilling、implementation、QA。この定義が曖昧なのは意図的で、phase は *「よし、これは片付いた」* と思った時点で終わる。

**phase boundary** とは 2 つの phase のあいだの隙間であり、この判断が属する唯一の場所だ。phase の途中には下すべき判断は無い。そのまま続けるか、残った作業を subagent に切り分けるかだ。phase の途中で compact すると、agent は筋を見失う。

## 5 つの選択肢

| 選択肢       | 何をするか                                                    |
| ------------ | --------------------------------------------------------------- |
| **Continue** | セッションに留まる。context switch は一切なし。                    |
| **`/clear`** | context window を空にし、何も無い状態から始める。                  |
| **`/handoff`** | 可搬な markdown ファイルを書き、それを種にどこででもセッションを立てる。 |
| **Subagent** | タスクを専用の context window へ送り、報告を受け取る。     |
| **`/compact`** | この context を圧縮し、その要約を種に新しいセッションを立てる。  |

## ツリー

境界では上から下へ辿れ。最初の **yes** が勝つ。

**1. このセッションのまま続けられるか?** yes になる条件は 2 つ: 次の phase がこの phase を **一次情報 (primary source)** として必要とするか、次の phase が収まるだけの [smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)（~150k tokens）が残っているか。grilling → implementation は標準的な yes だ: implementation が欲しいのは推論の逐語であって、その要約ではない。Continue はコストゼロ・損失ゼロなので、何よりも先にこれを除外しろ。

**2. その context は次に来るものと無関係か?** このセッションにあるもの（探索、判断、行き止まり）がすべて捨ててよいか? そうなら **`/clear`**。盤上で最も安い手だ: 時間がかからず、窓を丸ごと返してくれる。`/clear` は終端でもない。古いセッションは resume 可能なまま残る。

ここを誤ったときのコストは一方通行だ。*関連のある* context を clear すると、作ったものの背後にある **why** を失い、diff を読み返しても二度と戻らない。

**3. handoff が必要か?** `/handoff` の用途は狭い。必要になるのは次のときだけだ:

- **別の harness** へ乗り換える（Claude → Codex）、
- **別のディレクトリ**やリポジトリへ移る、
- **同僚**へ作業を送る、
- あるいは **phase の途中で**見つけた横道の作業を、今やっていることを脱線させずに fork する。

このリストが条項のすべてだ。`/handoff` が買うのは **可搬性**、つまり移動するファイルだ。移動するものが無いなら、必要ない。

**4. そのタスクは AFK でこなせるか?** キーボードから離れていても、舵取り無しで走らせられるほどきつくスコープが絞られているか? ならば **subagent** へ送り、このセッションには手を触れるな。自動レビューが標準的なケースだ: agent が diff を読んで報告するあいだ、あなたは必要ない。

**5. それ以外は `/compact`。** context に関連があり、同じ harness、同じディレクトリで、あなたが loop の中に居続ける必要がある。ツリーはここに着地し、しかも着地は頻繁だ。指示を添えろ（`/compact we're going to QA this area`）。そうすれば要約は次の phase が必要とするものを保つ。

`/compact` は **デフォルトだが、最初に手を伸ばす先ではない**。末尾にあるのは、上の 4 つの問いがどれもより安いか、より正確だからだ。ここから始めたときの failure mode は、要約が均してしまった判断について自信たっぷりに間違えている、まっさらなセッションだ。

## 一次情報と二次情報

**Continue** 以外のすべての手は、**一次情報 (primary source)** を **二次情報 (secondary source)** に変える。起きたままのセッションが、その要約に置き換わる。トレードオフの形は常に同じだ:

| 情報源                            | 情報量 | ノイズ | 動かせる余地 |
| --------------------------------- | ----------- | ----- | ------------ |
| 一次情報 (Continue)                | 完全        | 多い  | 少ない       |
| 二次情報 (`/compact`、`/handoff`) | 欠落あり    | 少ない | 多い         |

だから問い 1 が先に来る。留まるコストが節約分を上回るときにだけ、この欠落を支払え。

## これらは judgement call だ

これらの問いは客観的ではない。どれにも趣味が混ざっており、同じ境界でも日によって答えが変わりうる。価値があるのは、作業の途中ではなく境界で、**順番どおりに** 問うことの方だ。
